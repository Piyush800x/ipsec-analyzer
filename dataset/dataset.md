# The IPsec testbed dataset

Labelled IPsec sessions generated by the testbed in `backend/testbed/`. Every
row is a real tunnel between two containers, captured on the bridge they
share, with ground truth recorded from the configuration that built it rather
than from anything a parser inferred afterwards.

**Status: the generation runs have not been performed.** The schema, the
generator and the verification harness all exist and are tested; steps 8.1 and
8.3 need a Docker daemon and a kernel with XFRM, which were not available in
the environment this was built in. See [CHANGELOG.md](../CHANGELOG.md) under
Phase 8. Nothing in this document is describing data that exists on disk today.

---

## 1. Directory structure

```
dataset/
├── dataset.md              this file
├── dataset.yaml            manifest: seed, matrix version, image versions
└── sessions/
    └── <session-name>/
        ├── capture.pcap    classic pcap, filtered to the tunnel
        └── labels.json     ground truth (schema below)
```

One directory per session. `<session-name>` is `SessionConfig.name`, which is
stable for a given matrix row and seed, so a regenerated dataset overwrites
rather than accumulating near-duplicates.

## 2. How a session is produced

`backend/testbed/orchestrator.py`, in this order (LLD §10.2):

1. Create a user-defined bridge network and two peer containers.
2. Render `swanctl.conf` for both ends from one `SessionConfig`, so the two
   sides cannot disagree about what they are negotiating.
3. Start `tcpdump` inside the initiator, and **wait for it to report
   listening** before initiating — otherwise the IKE exchange is missed.
4. Bring the tunnel up and **assert an ESTABLISHED IKE SA and an INSTALLED
   Child SA**. A failed negotiation otherwise produces a capture full of
   retries carrying a label that says it is a working tunnel.
5. Generate traffic for the configured class and duration.
6. Tear the tunnel down *inside* the capture window, so the IKE DELETE
   exchange is recorded.
7. Stop the capture, refuse an empty one, and only then write the output
   directory.

## 3. `labels.json`

Three blocks, deliberately kept apart:

| Block | What it is |
|---|---|
| `dimensions` | What the matrix chose, in the testbed's own vocabulary (`aes128gcm16`, `ikev1-aggressive`, `v6`) |
| `expected` | What a correct parser should report, keyed by `SecurityAssociation` field and valued with **contract** enums |
| `not_observable_from_ike` | The fields in `expected` that **no** parser can recover from this capture, each with the reason |

That third block is load-bearing. Without it the verification harness would
flag a parser correctly reporting `UNAVAILABLE` as a mismatch, and the obvious
way to turn the harness green would be to teach the parser to guess — which is
the one thing this product must not do.

The `expected` values are the *configuration*, not a parser's opinion of it.
Two consequences worth stating plainly:

- `encryption_alg`, `encryption_keylen` and `integrity_alg` describe the
  **Child (ESP) SA**. Track A cannot observe those — the Child SA proposal is
  negotiated inside an encrypted exchange for both IKE versions — so it reports
  them as same-family inferences from the IKE SA. The matrix deliberately runs
  IKE on CBC even when ESP carries AEAD (IKEv1 cannot negotiate AEAD for Phase
  1 at all), so **those inferences are expected to diverge on every GCM row**.
  The harness scores them as `inferred`, not as mismatches.
- `traffic_class` is ground truth for Track B's classifier, not for any single
  `SecurityAssociation` attribute.

## 4. The matrix

`backend/testbed/matrix.yaml`, sampled by `backend/testbed/sampler.py` with a
fixed seed. Nine dimensions; the sampler produces 60 configurations covering
all 257 pairs from a cross-product of 3360. Re-running with the same seed
produces an identical list, which is what makes the resume manifest and this
dataset reproducible.

## 5. Verification

```bash
cd backend
uv run python -m testbed.verify ../dataset/sessions
```

Compares Track A's output against every `labels.json` and reports each field as
`match`, `honest_gap`, `inferred`, `mismatch`, `fabricated` or `not_reported`.
Only `mismatch` and `fabricated` fail. `fabricated` — a value reported where
ground truth says the field is unobservable — is the most serious outcome the
harness can produce, because it is a guess the report would present as a fact.

## 6. Versions that must not drift

Every session copies `/etc/testbed-versions.json` into its labels. strongSwan
decides the cryptography and tcpdump decides the packet geometry, so a silent
upgrade mid-dataset would split the corpus in two with nothing failing:

| Tool | Pinned version |
|---|---|
| strongSwan | `5.9.8-5+deb12u5` |
| tcpdump | `4.99.3-1` |
| tshark (analysis side) | `4.4.18` |

## 7. Licence and provenance

Synthetic throughout. Every packet was generated between two containers on a
private bridge; no capture contains real user traffic, real endpoints, or any
personal data. The pre-shared key is fixed, published in the repository, and
protects nothing.

Released under the repository's licence ([LICENSE](../LICENSE)).

**not** redistributed here and carries its own terms — obtain it from the
University of New Brunswick directly.

## 8. DVC

The captures are tracked with DVC rather than git: a full run is several GB of
PCAP, which does not belong in git history.

```bash
dvc pull                  # fetch the captures for the committed revision
dvc repro                 # regenerate (needs Docker + XFRM)
```

`dataset/sessions.dvc` records the content hash; the remote is configured in
`.dvc/config` and is deliberately not set to a public bucket, because the
captures are cheap to regenerate and expensive to host.
